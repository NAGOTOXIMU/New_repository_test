# 数据库规范落地改造总结

> **本文档说明：对着《数据库规范.docx》V1.0 做了哪些修改、每一处为什么必须改。**
>
> 改造日期：2026-10-12
> 改造策略：**以《数据库规范》7 张表为准，修改代码去适配数据库**（而不是改规范去迁就代码）
> 验证方式：真实 MySQL 库端到端跑通，60 项业务用例 + 11 个页面运行验证全部通过

---

## 一、一句话背景

改造前，项目里有**三套互不匹配的设计**同时存在：

| | 表名 | 用户表字段 | 状态表示 |
|---|---|---|---|
| 《数据库规范》 | `reservation_order` / `recharge_order` | `phone` / `nickname` | TINYINT 数字 |
| 项目代码 | `reservation` / `recharge` | `username` / `real_name` / `email` | 中文字符串 ENUM |
| 实测数据库 | `reservation_order` / `recharge_order` | `phone` / `nickname` | TINYINT 数字 |

**规范与数据库基本一致，但项目代码和它们完全脱节**——`repository/` 里 8 个模块的每一条 SQL 都打不中实际数据库，应用一运行就是 `Unknown column`。

所以这次改造的方向是：**让代码去贴规范和数据库**，同时把规范本身存在的 5 处逻辑缺口补上。

---

## 二、为什么要改：改造前的 4 类致命问题

### 问题 1：代码与数据库完全脱节（最严重）

实测数据库里根本没有代码要查的列：

| 代码里写的 | 数据库实际有的 | 后果 |
|---|---|---|
| `user(username, password, real_name, email)` | `user(phone, nickname, ...)` | 登录、注册全部 `Unknown column` |
| `store.name` / `store.phone` | `store.store_name`（无 phone） | 门店功能全挂 |
| `seat.seat_no` / `seat.zone` / `seat.price_per_hour` | `seat.seat_code` / `seat.area_type`（无价格列） | 座位功能全挂 |
| 表 `user_card` | **数据库里没有这张表** | 充值购卡 `Table doesn't exist` |
| 表 `reservation` | 实际叫 `reservation_order` | 预约功能全挂 |
| 表 `recharge` | 实际叫 `recharge_order` | 充值功能全挂 |
| 列 `admin.password` / `real_name` / `store_id` | 实际是 `password_hash`（无后两列） | 管理员功能全挂 |

### 问题 2：状态值用中文字符串，违反规范

代码里到处是 `status = '正常'`、`order_status = '待使用'`、`kind = '储值'`。
规范的第二节明确要求：**状态/类型字段统一使用 TINYINT，用数字代表状态，禁止使用字符串。**
实测数据库也确实是 TINYINT。

### 问题 3：防重复预约没有任何数据库级保证

规范第 11 张图要求"通过条件判断 + **原子插入**避免同一时段同座位重复预约"（防超卖）。
但实测数据库的 `reservation_order` 表上**一个唯一约束都没有**。
代码里只有"先查有没有，再插入"——这在并发下必然出错（两个请求同时查到没被占，然后都插进去）。
**这一条不修，系统的核心业务就是不可靠的。**

### 问题 4：规范自身有 5 处逻辑缺口（不补则功能无法闭环）

详见第四节。

## 三、改了哪些文件、为什么（按层）

### 3.1 数据库脚本层

| 文件 | 改了什么 | 为什么 |
|---|---|---|
| `db/sql/01_schema.sql` | **全部重写**：8 张表；每张表显式声明 `COLLATE utf8mb4_unicode_ci`；35 条索引；25 条 CHECK 约束；11 条外键（含 2 条复合外键）；补齐外键级联动作 | ①改造前表级排序规则跑成了 `utf8mb4_0900_ai_ci`（建表时没写 COLLATE，沿用了 MySQL 8.0 服务器默认），与规范的 `utf8mb4_unicode_ci` 不符；②规范第 3 节要求"约束规范"和"联合索引"，实测库里 CHECK 有 0 条、规范点名的 3 条联合索引一条都没有 |
| `db/sql/02_indexes.sql` | **从"建索引脚本"改为"索引核对清单"** | 原脚本用了 `DELIMITER`——这是 **mysql 客户端专有语法**，`db/init_db.py` 用 PyMySQL 执行时会直接 **报 1064 崩溃**。索引已全部并入建表语句，这样"建表即建索引"，不存在"忘了执行第二个脚本"的风险 |
| `db/sql/03_seed.sql` | **全部重写**：主数据测试数据，全部 `ON DUPLICATE KEY UPDATE` | 原文件只有注释、**一条可执行 SQL 都没有**。同时把卡种数据改成与新的计费口径一致 |
| `db/seed.py` | **新增** | 密码哈希必须用项目自己的算法生成，否则"灌进去的密码登不上"。用 Python 现算哈希，密码永远和 `services/password.py` 一致 |
| `db/init_db.py` | 修 `DELIMITER` 崩溃；加 UTF-8 输出；加建完自检（表数/外键数/CHECK 数/排序规则） | 见上面 `02_indexes.sql` 的原因；自检是为了让"建库是否真的符合规范"一眼可验 |

## 四、补掉的 5 处规范逻辑缺口

这 5 处是**规范自身的问题**，不补则功能无法闭环。**建议把它们并入《数据库规范》文档。**

### 缺口 1 ⭐ 缺少「用户持卡实例表」（最严重）

**规范的问题**：`card_type` 定义了三类卡（时长卡/次卡/储值卡），但**没有表记录"用户实际持有的那张卡"**。
资产只能落在 `user.balance`（元）和 `user.remaining_hours`（分钟）上——这是**每用户一份**，于是：

- 用户同时持有时长卡和储值卡时，无法说明**哪张卡**有多少钱、多少分钟；
- `card_type.value`（时长卡=分钟数，次卡=次数）**没有任何表可以承接扣减**；
- 充值到账后权益无处落账，**"充值购卡"业务无法闭环**。

**补充**：新增 `user_card` 表，资产按卡归属。
`user.balance` / `user.remaining_hours` 保留，但降级为**汇总冗余字段**（由 `user_repo.refresh_summary()` 在同一事务里重算），仅供列表页快速展示，**不再作为扣减依据**。

### 缺口 2 预约表缺少"取消后释放时段"的机制

**规范的问题**：规范定义了 `order_status` 有"已取消"，但**没定义取消后如何让时段重新可约**。
如果只把 `order_status` 改成 4，那条记录仍然占着时段，**那个时段就永久约不了了**。

**补充**：新增可空列 `active_flag`，并并入唯一索引：

```sql
active_flag TINYINT NULL DEFAULT 1 COMMENT '1=占用时段；取消时置NULL以释放唯一索引',
UNIQUE KEY uk_seat_slot (seat_id, reserve_date, start_time, end_time, active_flag)
```

> 后续修订：唯一键补上了 `end_time`（原键会误挡「同开始时间、不同时长」的预约），
> 并且在业务层加了座位级 `GET_LOCK` 来防「部分重叠」时段并发抢座。
> 老库升级见 `db/sql/04_migrate_uk_seat_slot.sql`。

取消时 `order_status=4` **且** `active_flag=NULL`。
利用 **MySQL 唯一索引允许多个 NULL** 的特性，时段被真正释放。

> 规范原文只写了"原子插入"，没写"取消"。这是必须补的另一半。

### 缺口 3 关键业务表缺少幂等键

**规范的问题**：规范第 5 节要求"杜绝扣了钱没订单/到账了没流水"，但 `recharge_order` 和 `reservation_order` **都没有业务单号**。仅靠自增主键，无法防"用户连点两次提交"和"支付回调重复通知"。

**补充**：两表各加 `order_no VARCHAR(32) NOT NULL` + `UNIQUE KEY`。

### 缺口 4 缺少价格/计费口径

**规范的问题**：`seat` 表只有 `area_type`/`has_socket`，**没有价格列**；`card_type` 只有 `price`（售价）和 `value`（价值），**没有"储值卡每小时扣多少钱"**。于是储值卡该扣多少无法确定。

**补充**（已实现，并把 `value` 的语义扩展到储值卡）：

| 卡类型 | 扣减方式 |
|---|---|
| 时长卡 `kind=1` | 每次预约扣 `duration` 分钟；`value` = 总分钟数 |
| 次卡 `kind=2` | 每次预约扣 1 次；`value` = 总次数 |
| 储值卡 `kind=3` | 扣 `小时单价 × 小时数`（不足 1 小时按 1 小时取整）；**小时单价 = `price ÷ value`**，此时 `value` 约定为"这张卡包含的小时数" |

例：100 元储值卡 `value=20` → 5 元/小时。`value=0` 时用常量 `config.STORED_HOUR_RATE` 兜底。
**管理员要调价，只需在卡种管理里把 `value` 填成小时数，不用改代码。**

### 缺口 5 `reservation_order` 的门店冗余可能不一致

**规范的问题**：`reservation_order` 同时有 `seat_id` 和 `store_id`。如果前端传错，就会产生"预约记录写 A 店、座位其实属于 B 店"的脏数据。

**补充**：用**复合外键**从数据库层封死：

```sql
-- seat 表补一个唯一键，作为复合外键的被引用键
ALTER TABLE seat ADD UNIQUE KEY uk_seat_id_store (seat_id, store_id);

-- reservation_order 的座位外键改为复合外键
CONSTRAINT fk_res_seat FOREIGN KEY (seat_id, store_id) REFERENCES seat(seat_id, store_id)
```

## 五、改造过程中发现并修掉的真实 bug

这些不是"改名"，是**真的会出问题**的缺陷：

| # | Bug | 后果 | 修法 |
|---|---|---|---|
| 1 | `db/init_db.py` 会崩溃 | 原 `02_indexes.sql` 用了 `DELIMITER`（mysql 客户端专有语法），PyMySQL 执行直接报 1064，**一键建库完全不可用** | 索引并入建表脚本；`02_indexes.sql` 改为核对清单 |

| 3 | `db/seed.py` 不幂等 | 原本没有固定主键，**每跑一次就插一批新行**（预约表从 5 行涨到 10 行） | 加固定主键 + 清理旧版种子行 |
| 4 | 登录页引用不存在的模块 | `admin_service` 根本没建，**管理员登录必然 `ImportError`** | 补建 `services/admin_service.py` |
| 5 | 管理端页面全是空文件 | 7 个页面文件只有一行文档字符串，**点过去就是白页** | 全部实现 |
| 6 | 数据看板没页面 | `stats_service.py` 写好了但没人调用 | 新增 `admin/5_dashboard.py` |
| 7 | `use_container_width` 已废弃 | 运行时刷废弃警告 | 全部迁移到 `width="stretch"` |
| 8 | 表级排序规则跑偏 | 库级是 `utf8mb4_unicode_ci`，但 7 张表全是 `utf8mb4_0900_ai_ci`，跨表 JOIN 可能报 `Illegal mix of collations` | 每张表显式声明 `COLLATE utf8mb4_unicode_ci` |
| 9 | `.env` 未创建 | 代码读不到 `DB_PASSWORD`，连不上库 | 创建 `.env`（已被 `.gitignore` 忽略，**不会进仓库**） |

## 八、维护约定

1. **`db/sql/` 和 `repository/` 是全组公共依赖** —— 改表结构前先在群里说，由一个人统一改，改完通知所有人。
2. **改了表结构，必须同步更新本文档和 `数据库规范落地对照与缺口补充.md`。**
3. 写 SQL 脚本时**不要用 `DELIMITER`**——`db/init_db.py` 用 PyMySQL 执行，不认这个客户端命令。
4. 状态值一律用 `config.py` 里的常量，**不要写魔法数字，也不要写中文字符串**。
5. 密码、密钥一律不进仓库（`.env` 已在 `.gitignore` 里）。
