## 二、规范缺口补充（必须同步回主规范文档）

实施过程中发现**规范自身有 5 处逻辑缺口**，不补就会出现「功能无法闭环」。以下为实际采取的补充，请数据库负责人把它们并入《数据库规范》。

### 缺口 1 ⭐ 缺少「用户持卡实例表」（严重）

**问题**：规范里 `card_type` 定义了三类卡（时长卡/次卡/储值卡），`user_card` 却不存在。资产只能落在 `user.balance`（元）和 `user.remaining_hours`（分钟）上——**这是"每用户一份"**，于是：

- 用户同时持有时长卡和储值卡时，`balance` 和 `remaining_hours` 无法说明**哪张卡**有多少；
- `card_type.value`（时长卡=分钟数、次卡=次数）**没有任何表可以承接扣减**；
- 充值到账后权益无处落账，「充值购卡」业务无法闭环。

**补充**：新增 `user_card` 表，资产按卡归属：

```sql
CREATE TABLE user_card (
  card_id           INT AUTO_INCREMENT PRIMARY KEY COMMENT '持卡实例ID',
  card_no           VARCHAR(32) NOT NULL COMMENT '卡号（业务唯一号）',
  user_id           INT NOT NULL COMMENT '持卡人ID（外键）',
  card_type_id      INT NOT NULL COMMENT '卡种ID（外键）',
  balance           DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '该卡储值余额（储值卡用）',
  remaining_times   INT NOT NULL DEFAULT 0 COMMENT '该卡剩余次数（次卡用）',
  remaining_minutes INT NOT NULL DEFAULT 0 COMMENT '该卡剩余时长（时长卡用，分钟）',
  expire_at         DATE NULL COMMENT '该卡到期日，NULL=永不过期',
  status            TINYINT NOT NULL DEFAULT 1 COMMENT '卡状态：1正常 0已冻结',
  create_time       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_card_no (card_no),
  KEY idx_uc_user_type (user_id, card_type_id),
  CONSTRAINT fk_uc_user FOREIGN KEY (user_id) REFERENCES `user`(user_id)
    ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT fk_uc_type FOREIGN KEY (card_type_id) REFERENCES card_type(card_type_id)
    ON DELETE RESTRICT ON UPDATE CASCADE,
  CONSTRAINT chk_uc_balance CHECK (balance >= 0),
  CONSTRAINT chk_uc_times   CHECK (remaining_times >= 0),
  CONSTRAINT chk_uc_minutes CHECK (remaining_minutes >= 0),
  CONSTRAINT chk_uc_status  CHECK (status IN (0,1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户持卡实例表';
```

**`user.balance` / `user.remaining_hours` 的定位**：保留，但降级为 `user_card` 的**汇总冗余字段**（由 `user_repo.refresh_summary()` 在同一个事务里重算），只为列表页展示快，不作为扣减依据。

### 缺口 2 预约表缺少"取消后释放时段"的机制

**问题**：规范把订单状态定义为 `1待使用 2进行中 3已完成 4已取消 5已过期`，但**没有说取消后如何让时段重新可约**。如果只把 `order_status` 改成 4，唯一索引仍被这条记录占住，那个时段就**永久约不了**了。

**补充**：`reservation_order` 增加可空列 `active_flag`，并把它并入唯一索引：

```sql
active_flag TINYINT NULL DEFAULT 1 COMMENT '1=占用时段；取消时置NULL以释放唯一索引',
UNIQUE KEY uk_seat_slot (seat_id, reserve_date, start_time, end_time, active_flag)
```

> 后续修订：唯一键补上了 `end_time`。原键 `(seat_id, reserve_date, start_time, active_flag)`
> 会把「同座位、同开始时间、不同时长」的正常预约误判成重复（09:00~10:00 与 09:00~11:00
> 互相挡住）。老库升级见 `db/sql/04_migrate_uk_seat_slot.sql`。

取消时 `order_status=4` **且** `active_flag=NULL`。MySQL 唯一索引允许多个 NULL，于是时段真正释放。

**规范原文第 11 图只写了"原子插入"，但没定义"取消"；这是必须补的一半。**

### 缺口 3 关键业务表缺少幂等键

**问题**：规范第 5 节要求"杜绝扣了钱没订单/到账了没流水"，但 `recharge_order` 和 `reservation_order` 都**没有业务单号**。仅靠自增主键无法防「用户连点两次提交」「支付回调重复通知」。

**补充**：两表各加 `order_no VARCHAR(32) NOT NULL` + `UNIQUE KEY`。

### 缺口 4 缺少价格/计费口径（座位表没有价格列）

**问题**：规范里 `seat` 只有 `area_type` / `has_socket`，**没有 `price_per_hour`**；`card_type` 只有 `price`（售价）和 `value`（价值），**没有"储值卡每小时扣多少钱"**。于是储值卡该扣多少无法确定。

**补充**（已在 `config.py` + `order_service.py` 实现，并把 `value` 的语义扩展到储值卡）：

- **时长卡** `kind=1`：每次预约扣 `duration` 分钟（`value` 是总分钟数）
- **次卡** `kind=2`：每次预约扣 1 次（`value` 是总次数）
- **储值卡** `kind=3`：扣 `小时单价 × 小时数`（不足 1 小时按 1 小时取整）
  - 小时单价 = `price ÷ value`，**此时 `value` 约定为"这张卡包含的小时数"**
    （例：100 元储值卡 `value=20` → 5 元/小时）
  - `value=0` 时退回常量 `config.STORED_HOUR_RATE`（默认 5.00）

管理员要调价，只需在卡种管理里把 `value` 填成小时数，**不用改代码**。

### 缺口 5 `reservation_order` 的门店冗余可能不一致

**问题**：规范里 `reservation_order` 同时有 `seat_id` 和 `store_id`。理论上前端传错就会产生"预约记录 A 店、座位属于 B 店"的脏数据。

**补充**：用**复合外键**从数据库层封死：

```sql
-- seat 表补一个唯一键，作为复合外键的被引用键
ALTER TABLE seat ADD UNIQUE KEY uk_seat_id_store (seat_id, store_id);

-- reservation_order 的座位外键改为复合外键
CONSTRAINT fk_res_seat FOREIGN KEY (seat_id, store_id) REFERENCES seat(seat_id, store_id)
  ON DELETE RESTRICT ON UPDATE CASCADE
```

实测：插一条门店与座位不匹配的记录 → 报 `1452 fk_res_seat`。
